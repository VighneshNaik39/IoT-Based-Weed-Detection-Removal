# WeedGuard — AI-Based Autonomous Weed Detection and Removal

This repository combines a Node.js dashboard/API, Python YOLO vision pipeline, and ESP32 robot/camera firmware. Hardware operation must be validated on the actual board before enabling automatic cutting.

## 1. Configure the hardware first

Replace `YOUR_WIFI_SSID` and `YOUR_WIFI_PASSWORD` in both firmware sketches with the same network credentials. Replace `CHANGE_ME_TO_A_LONG_RANDOM_KEY` in the robot firmware and backend `.env` with the same private key. Do not publish the real credentials or key.

- Use the same Wi-Fi SSID and password in both ESP32 firmware sketches.
- Robot firmware: `hardware/ESP-32/phase 5/ESP32_WeedRobot_v10_mdns/ESP32_WeedRobot_v10_mdns.ino`.
- Camera firmware: `hardware/ESP-32/camera/sketch_phase5_vision.ino` is configured for the standard AI-Thinker ESP32-CAM pin map (commonly paired with OV2640). It is not firmware for an ESP32-S3/LILYGO T-SIMCAM. Check the exact camera sensor and board revision before flashing.
- Set the same long random API key in the robot firmware `API_KEY` and `software/backend/.env` as `ESP32_API_KEY`.
- The Phase 5 robot firmware is configured for one L298N: ENA=12, IN1=13, IN2=14, ENB=25, IN3=27, IN4=26. Wire the two left motors in parallel to channel A and the two right motors in parallel to channel B only if the driver current rating is sufficient. Remove the ENA/ENB jumpers if your module has them so PWM speed control can work. One L298N may be undersized for four motors; verify stall current and driver temperature before ground testing.


### Electrical safety checks

- HC-SR04 ECHO can output 5 V; use a resistor voltage divider so the ESP32 GPIO receives no more than 3.3 V.
- Do not power the RS775 cutter motor from the ESP32 5 V pin or the camera board. Use a motor supply and relay/driver rated for the cutter's startup/stall current, with suitable fuse and wiring.
- Keep motor supply noise/current separate from logic power where possible, but connect grounds together when the control circuit requires a common reference.
- Battery level displays `--` until actual battery telemetry is implemented; do not treat it as a measured percentage.

## 2. Start the backend (Windows PowerShell)

```powershell
cd .\software\backend
Copy-Item .env.example .env
notepad .env
npm install
npm start
```

Fill the `.env` values before testing hardware. Keep `ENABLE_AUTOMATIC_CUTTING=false` initially. Open `http://localhost:5000/` and test `http://localhost:5000/api/status`.

## 3. Train the weed detector

In a second terminal:

Use Python 3.11 for the most predictable compatibility with the pinned computer-vision stack (the user's Python 3.14 installation may not have compatible PyTorch wheels for every dependency):

```powershell
cd .\software\ai-vision\scripts
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python train.py --weights yolov8n.pt --epochs 100 --batch 8 --imgsz 640
```

The repository does not contain actual trained model weights. Git LFS pointer files have been removed. Training requires internet access to download the official base model unless you already have a valid `yolov8n.pt` checkpoint. The trained `software/ai-vision/models/yolov8_weed.pt` will be generated by `train.py`.

## 4. Start live detection

After the backend can reach the camera and the trained model exists:

```powershell
cd .\software\ai-vision\scripts
python detect_stream.py --backend-url http://localhost:5000 --cam-url http://localhost:5000/api/detection/stream
```

The camera firmware starts mDNS as `weedguard-cam` and the robot hostname is `weedguard-robot`. Python detections are logged even if the robot is offline; the backend only permits automatic cutting when explicitly enabled and the robot status is safe. If mDNS does not work on your network, set `CAMERA_STREAM_URL` and `ESP32_IP` in `software/backend/.env`. The camera stream URL should end in `:81/stream` for the included AI-Thinker firmware (for example, `http://192.168.1.51:81/stream`). Camera status and capture are served on port 80.

## 5. Safety sequence

1. Test camera only.
2. Test YOLO on saved images.
3. Run live detection with automatic cutting disabled.
4. Test robot stop, obstacle detection, relay polarity, and cutter watchdog independently.
5. Only after controlled testing, set `ENABLE_AUTOMATIC_CUTTING=true` in `.env` and restart the backend.

Do not run the cutter while a person is near the blade. Keep the robot lifted or the cutting mechanism safely isolated during initial tests. The dashboard scan counter increments for analyzed frames. It reports `weedsRemoved: 0` until physical removal can be verified; detections and cutter commands are not proof that a weed was actually removed.

## Important limitation

This package fixes portable paths, broken merge-conflict markers, mDNS naming/import mismatch, hard-coded frontend camera IPs, fake dashboard metrics, and unsafe default automatic cutter activation. Hardware behavior still depends on the exact ESP32 board, Wi-Fi network, motor driver wiring, relay polarity, and a newly trained model. Those cannot be proven by source-code inspection alone.
